The suite is green at 115 tests, and every finding below survives it. That is the interesting part: the project's tests are unusually good at documenting what was deliberately designed — the scrollback offset arithmetic, the UTF-8 boundary guards, the mid-frame close contract — and the defects here sit in the seams those designs do not cover. Two were confirmed by running code against the real functions.

Findings

1

A binary file is silently destroyed the first time you save it

Critical Reproduced editor.rs:406
Definition

Opening any file that is not valid UTF-8 does not report an error. It loads the literal placeholder string "<binary>" into the buffer, marks the buffer clean, and leaves it fully editable. Saving then writes that placeholder over the original bytes.

Mechanism

OpenBuffer::open discards the read error rather than propagating it:

let text = std::fs::read_to_string(&path)
    .unwrap_or_else(|_| String::from("<binary>"));

read_to_string fails with InvalidData on any invalid UTF-8 byte. The unwrap_or_else turns that failure into ordinary text, so the buffer believes it holds the file's contents. Nothing downstream can tell the difference: too_large is false, dirty is false, and the status bar shows a normal text buffer. The first keystroke sets dirty, and save() writes self.text unconditionally.

Verified
Confirmed by running OpenBuffer::open and save against a real file. A 6-byte blob (FF FE 00 01 80 90) opened as the text "<binary>"; after one character was typed and saved, the file on disk was [60, 98, 105, 110, 97, 114, 121, 62, 33] — the nine ASCII bytes of <binary>!. The original content was gone.
Impact

Irreversible data loss, reachable by accident. Snor's explorer lists every file in the tree, so double-clicking an image, a .exe, a compiled .class, or any Latin-1 text file lands here — and the buffer looks completely normal until the save. The one mitigation is that the size usually differs, so the file is at least visibly wrong afterwards.

Fix. Return the error instead of substituting text, and refuse to open non-UTF-8 files with a clear message. If binary viewing is ever wanted, it needs a read-only buffer whose save is unreachable — the placeholder must never be a writable value.

2

--uninstall recursively deletes whatever folder the binary sits in

Critical installer/app.rs:56 install.rs:207
Definition

Any copy of the setup binary run with --uninstall schedules rmdir /S /Q on its own parent directory, with nothing verifying that the directory is a Snor install.

Mechanism

Launch::detect checks the flag first and returns immediately, ahead of the uninstall.info check that would otherwise validate the directory:

if std::env::args().any(|arg| arg == "--uninstall") {
    return Launch::Uninstall(dir);   // dir = exe.parent(), unvalidated
}

That directory then flows into install::uninstall, which removes four named files (ignoring any that are absent) and calls schedule_cleanup. The generated batch file contains:

rmdir /S /Q "{dir}" >NUL 2>&1

The /S flag is the whole problem: it deletes the entire tree, not the files uninstall just removed.

Scenarios
  • target\release\snor-setup.exe --uninstall → wipes every other build artifact in target\release.
  • Copy the installed uninstall.exe to the Desktop and run it → the Desktop is deleted.
  • dist\SnorSetup.exe --uninstall → wipes dist.

Nothing about the operation signals a recursive delete: the wizard shows three ordinary progress stages, and uninstall()'s own file loop touches only four names.

Fix. Require dir.join(MANIFEST).is_file() before honouring the flag, and otherwise fall through to the missing-payload screen. Independently, cleanup_script should refuse any directory that is not a verified install root — reject filesystem roots, %LOCALAPPDATA%, %USERPROFILE%, and drive roots outright.

3

A corrupt bundle length field panics the installer before the window opens

High Reproduced payload.rs:89
Definition

A footer whose 8-byte length field is near u64::MAX causes an arithmetic overflow and kills the process, instead of producing the "download a fresh copy" message the surrounding code is written to produce.

Mechanism

The subtraction below is guarded; the addition inside it is not:

let payload_start = len
    .checked_sub(FOOTER_LEN + payload_len)   // <- addition is unguarded
    .ok_or_else(|| "this setup file is truncated ...")?;

With payload_len = u64::MAX, FOOTER_LEN + payload_len overflows. This runs from Launch::detect inside main(), before run_native. In a debug build it panics with attempt to add with overflow; in release the addition wraps to 27, so checked_sub(27) succeeds, and the slice at line 91 becomes file[len-27 .. len-28] — start greater than end, which panics on the index. Either way the process dies.

Verified
Confirmed by running payload::parse behind catch_unwind with payload_len = u64::MAX: the call panicked at payload.rs:89 with attempt to add with overflow.
Impact

The release binary is windows_subsystem = "windows", so there is no console: the user double-clicks a damaged or bit-flipped download and the installer vanishes silently — no window, no message, no error. This is the primary entry path for a file the user fetched over the network, which is exactly where corruption is expected. The ordinary truncation case is handled correctly, which makes this the single hole in an otherwise careful parser.

Fix. payload_len.checked_add(FOOTER_LEN), mapping None to the same truncation error. Add the u64::MAX and u64::MAX - 1 cases to the existing truncation test — the current one only exercises a plausible length.

4

Terminal find keeps the oldest 200 matches and skips the live screen

High terminal.rs:490 terminal.rs:497
Definition

When a shell's history contains more than 200 matches, the find bar jumps to a match hundreds of lines back instead of the newest one, and never searches the live screen at all.

Mechanism

The history walk starts at the oldest offset and stops the moment the cap is reached:

for offset in (1..=oldest).rev() {   // oldest first
    screen.set_scrollback(offset);
    scan_row(screen, 0, cols, &needle, offset, &mut hits);
    if hits.len() >= cap { break; }        // stops early
}
if hits.len() < cap {                       // skipped when the cap was hit
    /* scan the live screen at offset 0 */
}

So hits fills with the 200 oldest matches. The live-screen block never runs, and recompute_find then lands on find_hits.len() - 1 — match 200 counted from the top of the scrollback, not the newest.

Scenario

A build prints 500 lines containing error. The user opens find and types error. The view jumps ~300 lines back into history and reports 200/200. The traceback that scrolled past one second earlier is never found. This inverts the stated intent at terminal.rs:2209 — "the newest match is the interesting one".

The existing test has exactly one match, so it cannot observe the cap.

Fix. Keep the newest cap rather than the oldest: walk oldest→newest and drop from the front, or scan forward with a ring buffer. Truncating from the tail also restores the live-screen scan, since the cap will no longer be spent on ancient lines.

5

Find state belongs to the terminal, not the tab — and leaks across tabs

High terminal.rs:1015 terminal.rs:2247
Definition

The hit list is computed against whichever tab was active when the query last changed, but jump_to_hit resolves the active tab again at press time. Switching tabs leaves the find bar reading the old tab's results and applies them to the new tab.

Mechanism

find_hits, find_pos and find_query live on Terminal, while the offsets they describe belong to one Session. recompute_find reads self.session_mut(); jump_to_hit calls self.session_mut() again, several tab switches later. Neither switch_to, new_tab, focus_session nor close_tab invalidates the list.

Scenario

Tab 1 is searched for error, giving 12 hits. The user clicks tab 2. The bar still shows 1/12, describing tab 1's content. Pressing next sets tab 2's scroll to a tab-1 offset and tints tab 2's markup.search at a matching row and column wherever the numbers happen to coincide — highlighting an unrelated cell in a different shell.

Fix. Key the find state by session id, or clear find_hits / find_pos in focus_session, new_tab and close_tab.

6

Find walks the entire scrollback on every keystroke, freezing the window

High terminal.rs:490 settings.rs:53
Definition

FIND_CAP bounds how many results are kept, not how much is searched. A single character typed in the find field can block the UI thread for seconds.

Mechanism

find_hits calls set_scrollback and scans a row for every offset in the history, each a scan of up to 400 columns. The loop breaks on the result cap, not on a scan budget — and a buffer dense with matches hits that cap only after the work is done. Meanwhile SCROLLBACK_MAX is 100_000 rows and set_scrollback feeds it straight into new parsers.

Scenario

scrollback = 100000 in settings, a session fills 100k rows, and the user types one character: up to roughly 100,000 × 400 cell reads in a single frame, on the thread that draws. egui stops repainting and the window is unresponsive.

The doc comment at terminal.rs:463 describes this as "one pass per frame of history", which understates it — it is one pass over the whole buffer, inside one frame.

Fix. Bound the number of offsets visited (min(oldest, 4000)), and/or spread the search across frames. Report a truncated result honestly rather than silently.

7

The Run button writes into a terminal the user cannot see

High terminal.rs:1440 app.rs:1574
Definition

Pressing Run after closing the terminal panel starts a build in a shell that stays hidden, so the output and the prompt both vanish.

Mechanism

Closing the last tab sets hidden (documented, intentional). Three callers are supposed to undo that, and reveal is the documented way back:

pub fn send_line(&mut self, line: &str, cwd: &PathBuf) {
    if self.sessions.is_empty() {
        self.new_tab(cwd);        // clears `collapsed`, never touches `hidden`
    }

new_tab clears collapsed but not hidden. Meanwhile reveal — which the other two callers (Ctrl+Tab and the status-bar toggle) use — sets hidden = false explicitly. Run is the odd one out.

Scenario

Close the terminal panel, then press Run in the editor. A shell spawns and cargo run executes, and the entire section stays hidden — the user sees no output, no prompt, and no error, and must know to press Ctrl+Tab to find out what happened.

Fix. Use self.reveal(cwd) in send_line instead of the bare new_tab call, which is what the existing comment already claims it does.

8

Ctrl+Shift+C is swallowed app-wide even with nothing selected

High terminal.rs:2167 terminal.rs:2183
Definition

The copy shortcut is consumed on every frame whether or not a selection exists, so it is unavailable to anything else in the app. Paste by chord works in normal mode and not in Flow Mode.

Mechanism

consume_shortcut runs unconditionally, ahead of the block that checks whether there is anything to copy:

let copy_key = ui.input_mut(|i| i.consume_shortcut(&CTRL | SHIFT, Key::C));
if copy_clicked || copy_key {
    let text = self.session().and_then(|s| s.selection.map(...));
    if let Some(text) = text && !text.is_empty() { ui.ctx().copy_text(text); }
}

Consuming an event is what makes it unavailable to every other widget, so the editor's copy only works because the editor happens to render first — an invariant documented in app.rs rather than enforced here. A future reordering silently breaks editor copy. consume_shortcut also matches logically, so Ctrl+Shift+Alt+C is eaten too.

The same asymmetry applies to paste: Ctrl+Shift+V is handled in ui (line 2183) but there is no equivalent in flow_ui, so the chord works in normal mode and does nothing in Flow Mode.

Fix. Consume the shortcut only when a selection exists and there is text to copy. Add the paste chord to flow_ui.

9

A split escape sequence in the title buffer is cut mid-character

Medium terminal.rs:242
Definition

The retained-tail buffer is trimmed by byte offset, so a multi-byte title straddling the 512-byte boundary is cut in half and rendered as a replacement glyph.

Mechanism

Keeping the last NOTIF_TAIL_MAX bytes:

let kept = if kept.len() > NOTIF_TAIL_MAX {
    &kept[kept.len() - NOTIF_TAIL_MAX..]   // byte offset, not a char boundary
} else { kept };

The slice lands wherever 512 bytes happens to fall. If that is inside a multi-byte UTF-8 sequence, from_utf8_lossy at line 228 yields U+FFFD, and the pane header paints a replacement character in the middle of an agent's self-reported title.

This buffer exists precisely for the multi-byte case — it is what lets a title split across two pty reads survive — so the truncation reintroduces the defect the mechanism was built to avoid.

Fix. Walk back from the cut point to the nearest char boundary before slicing, or keep a String and trim on a character boundary.

10

An empty install-folder field installs into the process working directory

Medium install.rs:105 app.rs:617
Definition

If the user clears the destination field, the installer does not complain. It installs into whatever directory the process happens to be running in.

Mechanism

install() takes the directory straight from the plan and immediately creates it:

let dir = &plan.dir;
std::fs::create_dir_all(dir)...?;

An empty path is a valid input to create_dir_all, which resolves it against the process working directory. So the app, the uninstaller and the shortcuts land in an arbitrary location — the same class of working-directory leak the first-run screen was written to eliminate, arriving through the installer.

Fix. Reject an empty or whitespace-only plan.dir before any write, and require it to be absolute.

11

current_exe().unwrap_or_default() degrades into empty-path operations

Medium installer/app.rs:54 installer/app.rs:621
Definition

When the executable path cannot be determined, the default is the empty path, and every downstream operation runs against it instead of failing cleanly.

Mechanism

unwrap_or_default() on a PathBuf yields PathBuf::new(). Then:

  • exe.parent() is None, so dir is empty. With --uninstall that becomes Launch::Uninstall(""), and rmdir /S /Q "" is handed to a detached batch file — harmless only by accident.
  • payload::parse_file(Path::new("")) fails with could not read : The system cannot find the path specified (os error 3), so the user sees a raw OS error naming an empty path instead of the styled "This copy of Snor Setup does not contain Snor" screen the code clearly intends.
  • In start_install, own is empty, so std::fs::read fails at install.rs:126.

Fix. Match on current_exe() explicitly. On Err, show the missing-payload screen with a real message and refuse --uninstall — this also closes part of finding 2.

12

Terminal grid rendering allocates per cell in the worst case

Medium terminal.rs:722
Definition

On screen content that alternates colour every cell, the grid renderer issues one append and one string push per cell — up to ~80,000 per frame on the UI thread.

Mechanism

Run coalescing flushes whenever the foreground or background changes, and the background is painted per cell for search and selection tints. A screen with alternating backgrounds — htop, a vim statusline, PowerShell's syntax-coloured Get-Content of minified JS — defeats the coalescing entirely.

Scenario

200 rows × 400 columns = 80,000 LayoutJob::append calls plus 80,000 String pushes every frame, on the thread that also draws the editor. Directly at odds with the project's headline memory and responsiveness goal.

Fix. Coalesce on equal (fg, bg) including the font (which is constant), and reserve cols capacity per row.

The packer and the launcher abort on a non-UTF-8 command line

Low snor-pack.rs:18 installer/app.rs:56
Definition

std::env::args() panics on any argument that is not valid Unicode, turning a bad path into a process abort instead of the clean error both tools already have paths for.

Mechanism

Both snor-pack and Launch::detect read arguments as String. args() panics on invalid UTF-8; args_os() does not. In the packer this destroys the release artifact mid-build rather than printing snor-pack: could not read …. In the launcher it aborts the wizard before the window is created.

Fix. Use args_os() and compare with OsStr, keeping PathBuf from the start so no lossy String round-trip occurs.

15

Splitting the last pane is refused, but the guard is unreachable

Low terminal.rs:2596 terminal.rs:2611
Definition

Both drag_col and drag_row apply a clamp and then re-check the same condition the clamp just guaranteed, so the second check can never fire.

Mechanism 
let a = (self.col_w[i] + dx / total_w).clamp(FLOW_FRAC_MIN, pair - FLOW_FRAC_MIN);
if a < FLOW_FRAC_MIN || a > pair - FLOW_FRAC_MIN { return; }  // unreachable
Why it is still worth fixing

f32::clamp panics when min > max, which happens whenever pair < 2 × FLOW_FRAC_MIN (0.24). Today flow_shape never produces a third column, so even fractions keep pair near 1.0 and the panic is unreachable — but the safety of the whole grid rests on an invariant three functions away, with the local guard that looks like it protects against exactly this being dead code. normalize() also divides fractions by their sum, so any future shape change moves the boundary.

Fix. Clamp against (pair - FLOW_FRAC_MIN).max(FLOW_FRAC_MIN) before calling clamp, and delete the unreachable guard.

17

Uninstall deletes whatever shortcut paths a hand-edited manifest names

High Batch 2 installer/install.rs:390 installer/install.rs:129
Definition

read_manifest pushes every shortcut= value into a PathBuf with no validation, and uninstall then calls remove_file on each one. Anyone who can write uninstall.info — a plain user-writable text file, documented as hand-editable — can point those lines at arbitrary files and have the uninstaller delete them.

Mechanism 
if key.trim() == "shortcut" {
    manifest.shortcuts.push(PathBuf::from(value.trim()));
}

No check that the path ends in .lnk, lives under a known folder, or was ever created by create_shortcuts. So shortcut=C:\Users\...\Documents\thesis.docx deletes that document during an otherwise ordinary uninstall.

Fix. Only accept manifest shortcut paths ending in .lnk under the Start Menu programs folder or the Desktop, and skip anything else. Failing closed on one bad line beats deleting a file the installer never created.

18

Explorer delete follows symlinks, so one click can empty another tree

High Batch 2 file_tree.rs:608 file_tree.rs:396
Definition

The delete path calls target.is_dir(), which follows symlinks, then remove_dir_all on the result. A symlink-to-a-directory is therefore deleted as a directory: everything inside the link target goes with it, including files outside the workspace root. The confirm modal names the link, not the files behind it.

Mechanism 
let res = if target.is_dir() {       // follows symlinks
    std::fs::remove_dir_all(&target) // empties the link target
} else {
    std::fs::remove_file(&target)
};

The same links are recursed through by build_tree via read_dir, so a cyclic link pair can also keep the 2000-entry walk busy expanding directories the user never asked to open.

Fix. Check symlink_metadata first: when the entry itself is a symlink, remove just the link with remove_file. In build_tree, skip directory-symlinks during recursion.

19

Sidecar install path reads an unchecked snor.exe with no size cap

High Batch 2 installer/app.rs:70 installer/payload.rs:111
Definition

When no payload and no manifest are present, Launch::detect falls back to a file literally named snor.exe beside the setup binary and reads the whole file with std::fs::read — no size check, no checksum. Whatever bytes carry that filename become the installed program.

Mechanism 
Some(sidecar) => match std::fs::read(&sidecar) {
    Ok(app) => Launch::Install(Bundle { exe: app, .. }),

The bundled path verifies FNV-1a before writing; the sidecar path verifies nothing. A stray multi-GB file named snor.exe is loaded fully into RAM (payload plus the copy install() makes is ~2x in memory), and a leftover or planted executable is installed and launched with the user's trust.

21

Closing a tab never kills its shell, so dead tabs keep their processes

Medium Batch 2 terminal.rs:1258 terminal.rs:1917
Definition

close_tab does self.sessions.remove(index) and nothing else: the Session (pty master, reader thread, Box<dyn Child>) is dropped. Dropping a portable-pty Child does not terminate the process — only the explicit kill() in Drop for Terminal does, and it runs once at app exit. Every closed tab leaks its shell until Snor quits.

Mechanism 
fn close_tab(&mut self, index: usize) {
    if index >= self.sessions.len() { return; }
    self.sessions.remove(index);   // handle dropped, process lives on

The header restart button has the same gap (session._child = None drops without killing), so each restart orphans one more shell — stray powershell.exe processes holding workspace files, each with a reader thread blocked on a pty nobody drains.

Fix. Kill before dropping in both places: if let Some(child) = session._child.as_mut() { let _ = child.kill(); } before removing or clearing the handles.

22

Editor save is not atomic: a crash mid-write leaves a truncated file

Medium Batch 2 editor.rs:421
Definition

save calls std::fs::write directly on the user's file. fs::write truncates first and streams second, so a power cut, killed process, or full disk between the two leaves a half-written file — the one writer in the tree whose input is unsaved human thought with no other copy.

Mechanism 
pub fn save(&mut self) -> std::io::Result<()> {
    std::fs::write(&self.path, &self.text)?;
    self.dirty = false;

The next poll_disk tick then happily re-stamps whatever survived. The same non-atomic pattern covers settings.save_to and the installer's write_file, but the editor is where it costs real work.

Fix. Write to a temp file in the same directory and rename it over the target (atomic replace on NTFS), keeping dirty true on any failure so the unsaved-work guards still fire.

File create/rename accept path separators, escaping the chosen folder

Definition

validated_name rejects empty names, ., .., and reserved characters — but never / or \. Typing sub\evil.rs or ../sibling.txt into the new-file or rename box sails through validation and is joined onto the parent, so the file lands somewhere the tree never showed, possibly outside the intended directory.

Medium Batch 2 editor.rs:554
Definition

open_file dedupes tabs by raw PathBuf equality only. The same file reached as src\main.rs vs an absolute path, via different letter case on Windows, or through a symlink / ..\ segment, opens a second tab with an independent copy. Terminal poll has no per-frame budget: one noisy shell freezes the UI

Low Batch 2 terminal.rs:1338 terminal.rs:1577
Definition

Terminal::poll drains every queued chunk from every session, and Session::poll loops try_recv until the channel is empty — all on the UI thread with no cap on chunks, bytes, or time. A shell dumping megabytes must be fully parsed and vt100-processed before the frame finishes, so egui stops repainting until the flood is over.

Mechanism 
pub fn poll(&mut self) {
    for session in &mut self.sessions {
        session.poll();            // each drains its channel to empty:
}
fn poll(&mut self) {
    while let Ok(chunk) = rx.try_recv() { out.push(chunk); }

The unbounded mpsc::channel behind this means a fast producer can also grow memory without limit while the UI is stuck.

Unknown shell = value silently keeps the default

Low Batch 2 settings.rs:179
Definition

The settings parser matches shell against five known keys and does nothing on any other value — no error, no notice. A typo (shell = powershel) or a value from a newer version quietly boots PowerShell while the file keeps claiming otherwise.

Mechanism 
"shell" => {
    if let Some(shell) = shell_from_key(value) {
        out.shell = shell;
    }   // else: silently keep whatever was there
}

Every other scalar in the same function is total and visible: bad numbers clamp and the panel shows what took effect. The shell is total but invisible — file and app disagree with nothing to reconcile them.

Fix. Record the ignored value so the settings panel (or a startup notice) can say unknown shell "powershel", using PowerShell. One ignored line should never look identical to a honoured one.
