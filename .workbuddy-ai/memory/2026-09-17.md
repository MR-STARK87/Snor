### Bug 1 — the cap notice was painted over the first pane's header

`flow_ui` painted `notice` at `rect.min + (8, 2)`, which is exactly where the
first pane draws its focus dot, title and cwd. Refusing a fifth terminal
overlaid "at the 4-terminal limit — close one first" on "powershell
C:\My work folder\Snor" and all three interleaved into unreadable mush at the
moment the user needed to read it. Reproduced at 4 panes, screenshotted.

Fix: `flow_ui` no longer paints it. `Terminal::notice_text()` exposes it and
`app.rs` draws it in the status bar beside the "Flow" word, where nothing can
collide. Normal mode's inline tab-strip notice is unchanged.

### Bug 2 — panes were sized after polling, freezing a torn TUI frame

`apply_size` ran inside `render_pane`, i.e. *after* `flow_ui` had already
called `poll()`. A resize therefore resized the ConPTY after that frame's
output had been drained; the TUI's repaint for the new size only reached the
grid on the next poll, and if the shell then went quiet the half-resized
frame stuck until an unrelated event forced a repaint.

Visible as OpenCode's ASCII logo half redrawn — top half at the new width,
bottom half still the old — frozen for 8+ seconds and unchanged by a forced
Ctrl+L. Reproduced and screenshotted.

Fix: new `Terminal::size_panes(area, cell)` runs **before** `poll()`, so the
output a resize provokes is drained in the same frame it was asked for. It
also subtracts `PANE_HEADER_H` + `PANE_GRID_PAD`, which the renderer's raw
`ui.available_size()` did not — so a shell is no longer told it owns a row
the pane does not actually draw.

`FlowView.cell` became unused and was removed.

### False alarm worth recording

A second "torn frame" turned out **not** to be one. The headless drag had
missed the divider and instead started a text selection inside a pane, which
paints a highlight over the text — at a glance it reads like corruption. If a
drag is meant to grab a divider, confirm the divider's real x first (measure
it out of the screenshot) or the result is a selection, not a resize.

### Hazard: `git checkout main` mid-flight leaves a deleted working tree

The first `git checkout main` was SIGTERM'd partway through, and the result
was dangerous: HEAD reported `main` while the tree was `dev`, and **51 tracked
files showed as deleted, including `src/syntax.rs`**. A commit made in that
state would have wiped them. `git status` was the tell.

- The kill left a zero-byte `.git/index.lock` with no git process alive.
  Cleared it manually after confirming via `tasklist` that nothing was running.
- Recovered with `git checkout -f dev`, then `git checkout -- .`.
- Lesson: after any interrupted git command, check `git status` and confirm
  tracked files still exist on disk before doing anything else.

### BUG: this git build cannot resolve `refs/remotes/*`

Symptom: `git branch -vv` showed `[origin/main: gone]` and
`git rev-parse origin/main` failed, even though the push and fetch had both
succeeded.

Diagnosis, in order:
- `.git/logs/refs/remotes/origin/main` had a correct, growing reflog while the
  ref itself did not exist. Contradictory.
- Writing the ref with `git update-ref` returned **exit 0 and did nothing**.
- A plain shell redirect to `.git/refs/remotes/origin/main` failed with
  "No such file or directory" because git was not creating the parent dir.
  It does **not** create `refs/remotes/<remote>/` on its own.
- After `mkdir -p` + a manual write, the ref resolved. But every subsequent
  `git fetch` removed it again -- even with `--no-prune`.
- Packing the refs into `packed-refs` did not help; a fetch stripped them out
  of the file.
- **Decisive A/B:** in the same `packed-refs`, `refs/tags/v0.6-snor` resolved
  fine while `refs/remotes/origin/main` did not. Same file, same format.

Conclusion: this is **PortableGit 1.2.0** at
`C:/Users/Zaida/.workbuddy-ai/binaries/PortableGit/versions/1.2.0/`, not a
stock git (real git here reports 2.55.0.windows.3 but the tree is the portable
wrapper). It reads `packed-refs` but skips `refs/remotes/*` entries, and
`fetch` drops them from that file. `.git/info/refs` is a hand-maintained
manifest listing only `heads/*` and `tags/*`.

### RESOLVED: it was a PATH shadowing problem, not a git bug

Zaida pointed out the machine already has a normal system Git for Windows at
`C:\Program Files\Git\`. It does -- and it works correctly. The real cause:

- The WorkBuddy shell puts its own Git root at **PATH position ~11**
  (`/mingw64/bin`), while the system Git (`/c/Program Files/Git/cmd`) sat at
  **position ~39**. So `git` resolved to the portable wrapper every time.
- `where.exe git` finds nothing and PowerShell's `Get-Command git` reports
  "not found" -- system Git is *not* on the Windows PATH, only inside this
  shell's PATH. Do not conclude from that that it is missing.
- Fix: `.bashrc` at `C:\Users\Zaida\.bashrc` strips any existing occurrence of
  `/c/Program Files/Git/cmd` from PATH and re-prepends it so the system Git
  wins. A `~/.bash_profile` that sources `~/.bashrc` was auto-generated by Git
  for Windows on first login-shell run.
- **Gotcha in the fix itself:** the system dir is *already* in PATH (just far
  too late), so a naive `case ":$PATH:" in *dir*` guard treats it as present
  and skips the reorder. Must remove-and-prepend, not check-and-add.

Verified with the system Git (2.49.0.windows.1): `git fetch origin` now
*creates* `origin/HEAD -> origin/main` and both refs survive repeated fetches.
`git branch -vv` shows `[origin/main]`, not `[origin/main: gone]`. Refs are
managed as loose files by the system git; `packed-refs` has no remotes lines.

Nothing destructive was needed: no `.git` recreation, no history rewrite. The
earlier manual loose-ref writes were harmless and the system git simply
adopted them.
